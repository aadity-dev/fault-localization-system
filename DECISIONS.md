## Load/burst testing decoupled from grid size
02-data-and-systems.md's 5,000-msg/10s burst target describes subdivision-
wide message volume (heartbeats + retries + duplicates across many
simultaneous events), not one fault producing 5,000 unique pole events.
We generate ~700-2000 poles (per 05-faq.md: "a few thousand is plenty"),
matching proportions not absolute scale, and test ingestion throughput
separately via simulator/load_test.py, which fires synthetic volume at the
/telemetry endpoint independent of how many real poles exist.

## Synthetic grid scale: ~700-2000 poles, not 38,400
Real network is 38,400 poles; brief explicitly says a few thousand is
sufficient as long as proportions match (~9% no device, ~60% DTs missing
topology, radial branching, spurs). Chose a smaller scale for
debuggability — able to manually verify individual fault scenarios by eye.

## Stack: Python (FastAPI + Postgres + Redis + Streamlit + NetworkX), not C++
Considered a C++ backend for the graph engine. Rejected: no mature async
web framework equivalent to FastAPI, heavier Docker/build complexity (ARM
vs x86 risk the brief explicitly warns about), and the actual graph
computation (MST/traversal over a few hundred poles per DT) is trivial at
this scale regardless of language — Python easily meets the 120s p95
localization target. Noted in ARCHITECTURE.md as a "what we'd revisit at
30-subdivision scale" item rather than building it now.

## Seed data generated once, committed to repo (not regenerated on boot)
data/pole_registry.csv and dt_registry.csv are pre-generated by
simulator/generate_grid.py and committed. Backend seed script loads these
static files into Postgres on startup rather than generating fresh data
each time — faster startup, deterministic (random.seed(42)), and
satisfies G3 (seeded on startup) without extra generation logic in the
container boot path.

## seq_on_line / parent_pole_id nullable by design in schema
These columns are Optional/nullable from the first schema draft, not
retrofitted later. This directly reflects the 60% missing-topology
condition described in 02-data-and-systems.md §3, which we treat as the
central design problem rather than an edge case.
